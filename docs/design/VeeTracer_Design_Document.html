1About this document

This document describes VeeTracer, a multi-tenant GPS tracking SaaS platform for the Indian market, covering the web dashboard, the VeeTracer mobile app and the VeeTracer Parent app. It consolidates every requirement agreed during the discovery discussions and turns them into a product scope, a system design, a data model and a phased roadmap.

Status: Approved on 18 October 2026 as the baseline for development. Any change after approval is recorded as a new version in the change table below.

1.1 How to read and request changes

  • Every feature has a unique ID (for example MAP-07, ALR-12). Refer to IDs when asking for changes.
  • Every feature has a phase: P1 core launch, P2 operations, P3 video & advanced, P4 growth. Later-phase features are still accounted for in the data model from day one, so adding them later needs no rework.
  • Section 22 lists the decisions that are still open. Those need an answer before or during Phase 1.

2Executive summary

VeeTracer lets businesses and individuals track anything that moves — vehicles, people, delivery staff, students' buses, assets, pets — on a live map, receive configurable alerts within seconds, replay history, manage drivers, routes and trips, monitor fuel and driving behaviour, and (later) watch live camera feeds. It is sold directly to customers on fixed monthly or annual plans in INR, and can be white-labelled and resold by partners.

4.2 Two independent access controls

ControlQuestion it answersConfigured by
Permissions (role → menu → action)What can this user do?Roles, menu-role mapping, user-role mapping
Data scope (branches + individual objects)Which objects can this user see?User → branch mapping, user → object mapping
  • A vehicle belongs to exactly one branch.
  • A user can be mapped to one or more branches and to individual objects. Example: one user sees their bike and their car on their own dashboard even if they sit in different branches.
  • Saved vehicle groups (e.g. "Night shift trucks") are only for filtering and reports; they never grant visibility.
  • Every API call, live update, report, export and webhook applies both controls on the server side.

4.4 Single Super Admin

  • Exactly one Super Admin account exists. The system refuses to create a second one.
  • Mandatory two-factor login. All Super Admin actions are written to the audit log.
  • A documented server-level recovery procedure covers loss of the password or second factor.
  • Super Admin can view any customer account ("view as") for support; every such session is logged.

6.2 Life of a position (hot path)

StepWhat happensBudget
1Device sends packet; gateway decodes, ACKs immediately, appends raw packet and normalised position to the stream< 50 ms
2Position processor reads the stream: bad-point filter, timezone, normalise attributes, update movement status, odometer, trip state< 100 ms

7.6 Data quality: jumps, drift and late data

ProblemHandling
Invalid fix, 0,0, too few satellites, poor accuracyFlagged invalid; not shown or counted
Impossible jumpImplied speed between points above the object-type limit (e.g. car 200 km/h, pet 50 km/h) → flagged
Parked driftWith ignition off and no motion, position frozen; movement under ~30 m ignored
Duplicates / future timestampsDropped / clamped and flagged
Late and out-of-order pointsInserted by fix time; trips and daily summaries for that period recalculated
LBS / Wi-Fi fixesShown as approximate; excluded from distance
Flagged points are kept (never deleted) and raw packets are logged, so data can always be audited or reprocessed with better rules.

7.7 Commands

Commands go out through the device's open TCP connection when online; otherwise they wait in a queue with an expiry and can fall back to SMS. Each command records who sent it, when, the device response and final status.

  • Validation and cost control: email and +91 mobile validation, duplicates removed, optional OTP verification for external numbers, SMS/WhatsApp usage estimate and plan limits shown before saving.
  • Send test checks every list; the delivery log shows sent / delivered / failed per recipient.

9.6 Evaluation

  • Rules are compiled per object and held in memory by the rules engine; changes are pushed instantly.
  • Previous state (inside/outside each geofence, over speed limit, ignition, status) lives in memory and Valkey, so each check is a constant-time comparison.
  • Time-based alerts (offline, idling too long, stayed too long, trip not started, late at stop, document expiry) run on a scheduler.
  • Anti-flapping on geofences and status changes: minimum dwell and boundary buffer.
  • Notification sending is asynchronous with retries; failures never delay other alerts.
  • SMS/WhatsApp usage is metered per company against plan allowance and credit packs.

15Video and cameras

  • Devices stream to ZLMediaKit, which converts JT/T 1078, RTMP and RTSP into WebRTC (lowest delay), HTTP-FLV or HLS for web and mobile.
  • Streams start only when someone opens them and stop automatically after a set time.
  • Alarm clips and snapshots are stored in object storage, linked to alerts and the history timeline.
  • Separate permissions for live view, playback and download; every view is logged.
  • Each live stream needs ~0.5–1 Mbps on the server; 50 concurrent viewers ≈ 50 Mbps upload. The media server scales independently.
