## 1. Design

**Constraint.** Open-source GraphHopper 11.1 has no `/matrix`. That is the commercial Directions API (`06` §2.2), and
production runs the open-source build at `ROUTER_URL=http://127.0.0.1:8989` with the `car` CH profile
(`ops/deploy/linux/maps/graphhopper.yml`). The matrix is therefore built from `GET /route` (option M1). There is no
second engine URL: the builder reads the provider's single `ROUTER_URL` + `ROUTER_ENGINE=graphhopper` config (R-3), so
an unset or `valhalla` engine is refused (`ENGINE_NOT_SUPPORTED`).

| Step | What | Why |
|---|---|---|
| Validate | Each point must be a finite WGS84 coordinate inside the India bbox (lat 6–37, lng 68–98). Other points are reported per point as `INVALID_INPUT` / `OUTSIDE_COVERAGE` and **excluded**: their row and column are null. | A bad point is not dropped silently, and its position is never changed. |
| Snap | One zero-length `/route` (`point=p&point=p`, `calc_points=true`) per point returns the snapped waypoint, so `snapDistanceM` = haversine(input, snapped). A 400 "Cannot find point" gives `POINT_NOT_ON_ROAD`. A point more than `ETMS_MATRIX_MAX_SNAP_M` (500 m) from the road gives `FAR_FROM_ROAD`. Both are excluded. An engine failure gives `NOT_CHECKED` (the point is not excluded). | This uses the same profile and `snap_preventions` (tunnel, bridge, ferry) as every matrix cell. `/nearest` ignores the profile. |
| Cache | Valkey read of every requested cell (see §2). | Stable home and stop locations are re-planned daily (`06` §7 estimates > 90 % hits). |
| Anchor probe | Route anchor ↔ every point. If p cannot reach anchor a but q reaches a, then p cannot reach q (otherwise p → q → a would be a route), so those cells are **proven** no-route without a call. The same holds the other way for "a cannot reach p". A point with no route either way is reported `DISCONNECTED`. When the first anchor is itself the island, up to three anchors are tried. | Isolates islands and one-way traps in O(n) calls. The probe cells are matrix cells anyway, so a full matrix pays nothing extra. |
| Walks | The remaining cells between mutually reachable points are covered by an **Euler cover** (Hierholzer on the requested arcs, balanced through a virtual node): each request `point=p0…pk&details=leg_time&details=leg_distance` answers up to 50 cells (`ETMS_MATRIX_LEGS_PER_REQUEST`). A complete digraph is one closed walk, so every cell is computed exactly once and no cell is computed that was not asked for. | With CH, each leg between via points is its own shortest-path query, so this cuts HTTP requests by roughly 50×. |
| Walk check | Strategy `auto`: the first walk per graph version per process is checked against 3 single-pair routes (time within max(0.5 s, 1 %), distance within max(2 m, 1 %)). A mismatch makes the graph `rejected`. Missing or merged per-leg details make it `unsupported`. In both cases the builder uses pairs only. | The builder never trusts walk numbers it has not verified on this graph. |
| Pairs | `calc_points=false&instructions=false`, one cell per request: for cells next to suspect points, and for everything else when walks are not trusted. Transient failures (5xx, timeout, connection) are retried up to 3 attempts. | This is the robust fallback. |
| Caps | One process-wide **adaptive in-flight limit** (default 3, max 8): after each window of 20 requests, a p95 per leg above 60 ms halves the limit and a p95 below 20 ms adds 1 back. A **build gate** allows 2 builds at once with a queue of 8; beyond that the answer is `LIMIT_EXCEEDED`, `retryAfterS: 30`. There is a **total budget** (default 120 s) and a **breaker** (8 consecutive transport failures). | R-5: GraphHopper uses one core per request, so 3 in flight leaves at least 3 of the 6 vCPUs for tracker ETAs, map matching, PostgreSQL and the API. The adaptive limit also yields when *other* GraphHopper users slow it down. |
| Result | `COMPLETE`: every requested cell is a number or a confirmed no-route. `PARTIAL` / `UNAVAILABLE`: `unknownCells` lists the cells that are null **only because the engine did not answer**, with `degraded {reason, message, retryAfterS}`. | Same split as R2 `routeStatus` (`NO_ROUTE` vs `UNAVAILABLE`). An unknown cell is never a number, never a no-route and never cached. The cells already done are cached, so a retry resumes. |

No straight-line, default-speed or symmetric (d(i,j) := d(j,i)) number is ever produced. The stub's road model is
deliberately asymmetric, so a symmetric shortcut would fail the tests. Straight-line distance is used only to *choose*
which cells a sparse request asks for (`sparse.ts` `kNearestPairs`). Provenance on every result:
`{ source: 'engine_free_flow', calibrated: false, liveTraffic: false }`.

## 2. Cache

- Keys: `vt:etms:mx:<graphTag>:<c|s>:<hash>`. `graphTag` = HMAC-SHA256(graph version) truncated to 6 bytes. `hash` =
  HMAC-SHA256(profile | from | to, coordinates rounded to 5 dp ≈ 1.1 m) truncated to 15 bytes, base64url. The HMAC key
  is derived from `ETMS_ROUTING_CACHE_SECRET`, else from `JWT_SECRET`. With neither set, the key is random per
  process (nothing is shared). **No coordinate or graph name is readable from a key.** The tests assert this on the
  in-memory client and on real Valkey.
- Graph version: `ETMS_ROUTING_GRAPH_VERSION` if set; otherwise `/info` → `gh-<version>|<data_date>|<import_date>`,
  memoised for 5 minutes. A re-import changes `import_date`, so the keys change; changing the CH profile requires a
  re-import. If `/info` has neither date, **the cache is off for that build** and the build itself still runs.
- Values: `<ms>,<dm>` or `x` (no route); snaps `d<dm>` / `d` / `x` / `o`. TTL `ETMS_MATRIX_CACHE_TTL_SEC` = 30 d.
- Memory cap: a per-graph counter of cells written. At `ETMS_MATRIX_CACHE_MAX_CELLS` (200k ≈ 30 MB at about 150 B per
  key) the cache becomes read-only (`stats.cacheFull`). The counter expires with the keys.
- Every Valkey error counts as a miss or no write, so the cache can neither fail nor block a build.

## 3. API for the routing worker (P8)

```ts
// Nest: RoutingModule exports MatrixBuilder and ROUTING_PROVIDER (GraphHopperProvider with the builder attached).
import { MatrixBuilder } from 'apps/api/src/routing/matrix/matrix-builder';
import { kNearestPairs } from 'apps/api/src/routing/matrix/sparse';

const build = await matrixBuilder.buildMatrix(points /* {lat,lng}[], index = optimiser locationIndex */, 'car', {
  pairs?: [from, to][],          // sparse: e.g. kNearestPairs(points, 40, depotIndexes); omitted = full n×n
  budgetMs?: number,             // default ETMS_MATRIX_BUDGET_MS (120 s)
  maxSnapDistanceM?: number,     // default 500
  signal?: AbortSignal,          // job cancel → LIMIT_EXCEEDED "cancelled"
  onProgress?: (done, total) => void | Promise<void>,
  noCacheRead?: boolean,
});
// build.status 'COMPLETE' | 'PARTIAL' | 'UNAVAILABLE'; build.degraded {reason, message, retryAfterS} | null
// build.durationsS / distancesM: (number|null)[][]  → optimiser matrix.durationsS / distancesM as is (null = forbidden)
//   ONLY when status === 'COMPLETE'. On PARTIAL: retry later (cache resumes), or treat unknownCells per policy.
// build.points[i]: { snapDistanceM, issue: INVALID_INPUT|OUTSIDE_COVERAGE|POINT_NOT_ON_ROAD|FAR_FROM_ROAD|DISCONNECTED|NOT_CHECKED|null, excluded }
//   → show excluded passengers as "pickup point needs fixing", not as unassigned for capacity.
// build.unknownCells, build.graphVersion, build.stats (requested/cached/computed/inferred/noRoute/unknown/engineCalls/…)
```

`RoutingProvider.matrix(MatrixRequest)` (sources × targets, optional `pairs`) runs the same build. It merges the points,
dedupes them at about 1 m, and returns `ok: true` **only** for a COMPLETE build, with `cells` and `invalid[]`.
Otherwise it returns `{ ok: false, degraded, message, retryAfterS }` with no partial numbers, as the provider rule
requires. `RoutingProvider.locate(points)` gives `{ onRoad, snapDistanceM (-1 = no road) }[]`.
`capabilities().matrix` = `{ native: false, maxSyncCells: 2500, maxAsyncCells: 360000 }` when wired.

**Gate:** `ETMS_ROUTING=on` (and `ETMS` not `off`). Off by default, which answers `ENGINE_DISABLED`.
**Env:** `ETMS_MATRIX_CONCURRENCY` (3), `_MAX_BUILDS` (2), `_QUEUE` (8), `_BUDGET_MS` (120000),
`_LEGS_PER_REQUEST` (50), `_STRATEGY` (`auto` | `walk` | `pairwise`), `_SLOW_LEG_MS` (60), `_FAST_LEG_MS` (20),
`_FAIL_LIMIT` (8), `_MAX_POINTS` (600 = solver LIMITS), `_MAX_SNAP_M` (500), `_CACHE_TTL_SEC` (2592000),
`_CACHE_MAX_CELLS` (200000), `ETMS_ROUTING_GRAPH_VERSION`, `ETMS_ROUTING_CACHE_SECRET`.

**System Health:** every build publishes `vt:etms:mx:stats` (1 h TTL): builds, degraded builds by reason, p50/p95 ms
per cell, cache hit ratio and the last build. `SystemHealthService.etmsMatrix()` reads it when ETMS_ROUTING is on.
`checks.ts` raises `maps.etms-matrix` (WARN: last build not complete) and `maps.etms-matrix-slow` (WARN: p95 above
50 ms per cell).

## 4. Measured cost

**No GraphHopper was reachable locally** (no Java on this PC; production is out of bounds). All numbers below are
against the in-process matrix stub on Windows 11 / Node 22.23.4. They measure **the builder's own overhead and request
counts**, not GraphHopper. **The B1–B3 sign-off needs a run of the same script on the staging host C3** with the GH 11.1
India graph:
`npx tsx scripts/etms-matrix-bench.ts --url http://127.0.0.1:8989 --gh-pid <GH pid> --k 20,40,60 --json b.jsonl`.

|---|---|---|---|---|
| 25 | 0.01–0.03 | 0.02–0.05 | 0.11–0.25 | 0.11–0.38 |

The first pairwise run at n=200 took 27–43 s and used 28–36 s of CPU. That was **quadratic**: `AbortSignal.any()`
with the long-lived build signal on every request. It is fixed (one controller per request, listener removed) and is
now linear, at about 0.24 ms of client time per cell.

### 4.3 Modelled engine cost (stub delay per leg; Windows timer granularity ≈ 15 ms, so each request costs at least ≈ 15 ms)

| n (Bengaluru) | walk wall s | pairwise wall s |
|---|---|---|
| 25 | 1.17 | 3.21 |
| 50 | 3.40 | 13.78 |
| 100 | 12.05 | 51.71 |
| 200 | 43.69 | 236.5 |

The in-flight cap held (stub peak 3 with cap 3). These figures model a fixed per-request cost plus a per-leg cost, so
they show **that per-request overhead dominates pairwise M1**. They are not GraphHopper numbers.

**What to expect on C3 (Estimate, to be replaced by the measurement).** CH cost is per leg, whether the leg comes
from a pair or a walk. With `06`'s 2–10 ms per CH query at 3 in flight, a 200 × 200 full matrix is 27–130 s of
GraphHopper work spread over 3 cores. B2's < 60 s target therefore needs CH at ≤ 4.5 ms per leg, **or** sparse k = 40
(about 9.6k cells, 6–32 s), **or** the cache (daily re-plans). The walk strategy removes about 39k HTTP round trips
and JSON parses per 200-point matrix, which pairwise M1 would otherwise spend on top. Walk requests carry
`calc_points=true` because path details need points, so GraphHopper also encodes the geometry: measure the GH CPU per
matrix with `--gh-pid`.
