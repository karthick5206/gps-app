## 2. Security review findings

| # | Status | Fix |
|---|---|---|
| **M1** | Fixed | ARRIVED, DEPARTED, BOARDED, NO_SHOW, DROPPED and COMPLETE_TRIP are evaluated and stored at `max(occurredAt, actualStart)`. The 48 h / window clock rule is still checked on the device time first; clamped rows carry `data.clampedToStart`. ARRIVED is checked against the stored `Position` track (valid fixes within ± 2 min of the time, ≤ 50 per arrival) plus the live fix: any fix near → `gps`, fixes but all far → `NOT_AT_STOP`, none → `unverified_location`. After an unverified arrival, NO_SHOW waits 5 min from `max(actualArrival, receipt of that ARRIVED)`; earlier it is `RETRY WAIT_NOT_ELAPSED` (not stored, the queue resends). A NO_SHOW accepted after an unverified arrival is flagged (`data.review`) and writes a SYSTEM `NO_SHOW_REVIEW` trip event (dispatcher timeline, web label) plus `noShowReview` in the audit. The driver never sees it. The report's repro (P1) is a test: the backdated ARRIVED is clamped to the trip start, meets the far live fix and is `NOT_AT_STOP`; without any fix it is accepted as unverified and both no-shows stay blocked. |
| **M2** | Fixed | At most one accepted REPORT_DELAY per trip per 15 min (others `DUPLICATE TOO_FREQUENT`). Relay TRIP_DELAYED dedupe key `delay:<trip>:<15-min bucket of the report's receipt>:<user>`, only while the trip is STARTED / IN_PROGRESS or the passenger's pickup is ≤ 60 min after the report. `POST /trips/:id/events`: 30 batches per driver login per minute (Valkey window, in-process fallback), else 429 `RATE_LIMITED` (the app's queue keeps the events). Repro P2 (50 reports in one batch) is a test: 1 accepted, 1 TRIP_DELAYED for the passenger. |
| **M3** | Fixed (native build needed) | `expo-screen-capture` ~58.0.6, installed with `npx expo install` in `apps/mobile` (SDK 58 version; package-lock edited only for this package). `DriverTripScreen` calls `usePreventScreenCapture` through `screen-guard.ts` (FLAG_SECURE on Android); a no-op on web. Tests use a recording stand-in for the native hook. **This is a new native module: it needs a new dev / release build. EAS was not run and `eas.json` was not changed.** |
| **L1** | Fixed | `reasonCode` must come from the closed list of the event type (`DRIVER_DELAY_REASONS`, `DRIVER_BREAKDOWN_REASONS`, `DRIVER_NO_SHOW_REASONS`, new `DRIVER_EARLY_DROP_REASONS` for DROPPED); anything else, or a reasonCode on another type, is a per-event `REJECTED VALIDATION_FAILED`. Erasure now replaces `data.note` on REPORT_DELAY / REPORT_BREAKDOWN of every trip the passenger rode with the erasure mark (scrub, not retention) and clears free-text `reasonCode` values on the passenger's seat events. |
| **L2** | Fixed | A stop whose point is hidden (no consent, or L7) is never GPS-checked: ARRIVED is accepted as `unverified_location` (so the M1 receipt rule and review apply), and `radiusM` is null whenever `pointHidden` is set. |
| **L3** | Fixed | The relay keeps a high-water mark of `receivedAt` (Valkey `vt:etms:notify:hwm`, stored after the notifications commit), reads from it with a 24 h cap (5 min overlap for late commits; a full page of 2000 continues from its last event), and writes `vt:etms:notify:state` `{at, hwm, full}`. System Health: `pipeline.etms-notify-relay` WARN after 5 min without a completed pass, CRITICAL after 30 min (`HEALTH_ETMS_RELAY_WARN_MIN` / `_CRIT_MIN`), and `pipeline.etms-notify-relay-backlog` WARN when a pass hit the page limit. Off when ETMS or `ETMS_NOTIFY_JOB` is off. |
| **L4** | Fixed | The manifest ACCESS audit is written without dedupe when Valkey fails; start (incl. replay / ALREADY_STARTED) and events responses are audited like `GET /trips/:id`; details carry `exactPoints`. |
| **L5** | Fixed | `sync?since=` is clamped to now − 48 h (an older cursor returns the full trip list, as a first sync); DRIVER_CHANGED is filtered on `data->>'from'` in SQL, newest first, `take` 500. |
| **L6** | Fixed | `@ArrayUnique(clientEventId)` on the batch DTO (400); the service also evaluates a repeated id only once. |
| **L7** | Fixed | A personal stop whose linked seats (and the owner's seats on the trip) are all CANCELLED is hidden: `pointHidden: PASSENGER_CANCELLED`, lat / lng / label / radius null. The consent reason wins when both apply. |
| **I1** | Fixed | `duty/trip`, `duty/report` and `commute/trip` accept only a UUID route id (`routeUuid`), else redirect to the section home. |

## 4. Privacy guarantees kept

The driver sees only their own trips (isolation matrix and completeness guard pass); names are "First L.", no contact;
points only with consent (and now never for cancelled-only stops, never with a radius when hidden); push data stays
`{kind, tripId, notificationId}` with generic text; `NO_SHOW_REVIEW` and `changeSetId` carry ids only; map styles
untouched.

## 6. For the owner / deploy

- **New native build needed** for `expo-screen-capture` (driver and passenger shells share the binary). Until then, a
  dev client without the module logs an error and does not block capture.
- New System Health checks `pipeline.etms-notify-relay*` start reporting once the API runs the relay.
- Behaviour changes for drivers: a second delay report within 15 min is acknowledged but not re-sent to passengers; a
  no-show after an arrival the GPS could not confirm waits 5 min from when the server received the arrival and is
  flagged for the dispatcher; reason codes must be from the app's lists.
- Still open from QA (out of this scope): device / emulator / Maestro tests, doc 12 E5 sim scenarios and durable SOS.
