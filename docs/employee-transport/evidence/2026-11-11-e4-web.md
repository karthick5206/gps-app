# E4 WP 4.5 — web route planner (doc 17 §7 P10) — evidence

Branch `etms/e4-web` (from `etms/e4` 2146106). Agent E4-G. Synthetic data only; no production access; no outside map hosts.

## What was built

Menu **Transport → Route planning** (`etms_planning`, `/transport/planning`), plan page `/transport/planning/:id`.
Code: `apps/web/src/features/transport/planning/`.

| Screen | Content |
|---|---|
| Optimise | Service date, direction (IN / OUT), sites, shifts (one plan per shift), vehicles with seats (vehicles without seats listed as excluded), **explicit objective weights** (every weight must be set, 0–10, nothing assumed), time limit. One job per plan: state, phase, progress %, attempts, **cancel**; failure reason as text (routing unavailable, optimiser busy / unavailable, limits, …). Disabled with the reason and a link to the dispatch board when the engine is down. |
| Plans | Plans of the day / direction with status, counts, version; tick 2–4 to compare. |
| Compare | Metrics only (server `GET /compare` + ride times / ETA quality from the details of the same version). Matrix on desktop, one card per plan on a phone. "Best" only where unambiguous (vehicles, distance, unassigned). **No overall winner unless weights are set**; weighted score and "Best by your weights" then. Delta vs baseline. "Keep this, discard the others". |
| Plan review | Metrics (vehicles, km, drive time, longest ride, warnings, unassigned / passengers), routes with vehicle / plate / driver, seats bar text, per-route stop list with engine ETA (labelled uncalibrated · no live traffic) or the reason there is none, unassigned passengers with the reason each, warnings, map, history. |
| Edits (explicit actions, no drag) | Up / down, **Move to…** (booking → `POST move-passenger`, pickup + drop together), **change vehicle**, **lock / unlock route**, **pin / unpin stop**. Every edit sends `expectedVersion`; the re-check (`violations`) is announced (aria-live + toast); `degraded` shows "routing unavailable … nothing was estimated"; 409 `PLAN_STALE` reloads and says so. |
| Publish | Confirmation dialog (trips to create, passengers seated, unassigned stay in the queue; warnings must be acknowledged). `Idempotency-Key` per (plan, version), kept for retries, freed on 4xx. Per-route refusals (`PLAN_NOT_PUBLISHABLE`, E3 codes such as `VEHICLE_BUSY`) listed by route. After publish: links to each E3 trip and the dispatch board. |
| Discard | Confirmation; plan becomes CANCELLED (history kept). |

Rules carried in `planner-format.ts` (pure, unit-tested):
- An ETA is shown only when the engine produced it (`EtaModel.source` engine_*); `live_heuristic` never; null when `degraded`. No straight lines, default speeds or browser estimates; map lines are engine geometry only.
- Map points: only stops the API sent coordinates for (`pointHidden` → not drawn, counted in a note); personal points rounded to 4 decimals unless the plan view is `precise`. Lists never show addresses for personal points.
- Gate: web flag `etmsRouting` (off in production builds, `VITE_UI_FLAGS=etmsRouting` or `localStorage vt.flags`) **and** the API reports routing enabled; menu hidden otherwise; the pages answer Not found without the flag.

Salvaged from the routing branch (rewritten to the new contracts and E3 patterns): vehicle colours (Okabe-Ito), `routesOf` / `moveStop` / `shiftStop`, unassigned-reason labels, access label, job progress / cancel, change-history labels, violation labels. `RoutePlannerPage` / `PlanEditor` generic-stop UI not ported.

### Browser scenario (Playwright-core + local Chrome, no global install)

`docs/employee-transport/evidence/e4-web/planner-scenario.cjs` drives the Vite dev server with the dev-only synthetic API
(`localStorage vt.plannerMock = 1 | engine-down`) and route-mocked auth / shifts / dispatch board, at **390 px** and
1280 px: optimise (refused without weights → explicit weights → job progress → done), second scenario, plans, **compare
with weights**, review, move down, pin, move to another route (re-check), publish confirmation, published trip links,
**engine down** (optimise blocked with "Routing unavailable"). Result: every step passed, **no sideways scroll** at 390
px or 1280 px (`screenshots/report.json`), no page errors. Screenshots in `screenshots/`.

Run: `WEB_PORT=5181 npx vite` in `apps/web`, then
`PLAYWRIGHT_CORE=<path to playwright-core> CHROME_PATH=<chrome.exe> node planner-scenario.cjs <outdir> http://127.0.0.1:5181`.

Limits: the basemap style (`/tiles/styles/*.json`) is not served by the dev server here, so maps show markers on an
empty background (no road lines; the map draws lines only once the style loads). Against the real API this is
**pending for QA** (staging with GraphHopper + optimiser + worker), including the doc 17 P10 gate "0 ETAs with a live
source when the engine is down" end to end (unit + mock scenario cover the client side).

## Integration points left (for the Lead / E4-E / E4-F)

1. **Plan creation**: no `POST /transport/route-plans` yet. The planner sends `CreateRoutePlanRequest + objectIds[]`
   (one call: plan from the day's bookings for direction / shift / site + its vehicles) and shows "Creating plans from the
   day's bookings is not available on this server yet" on 404 / 405.
2. **Capabilities**: no `GET /routing/capabilities` yet. The client falls back to: plans API 404 → off; dispatch board
   `routingAvailable` → engine reachable; optimiser / worker health assumed until a job says otherwise.
3. **Jobs API permission**: `routing/jobs` is gated on `etms_dispatch` (comment: until `etms_planning` exists). It now
   exists; switch to `etms_planning` create (optimise) / view.
4. **Weights**: the jobs API takes only `objective` (forbidNonWhitelisted); the planner derives it from the weights and
   keeps the weights for compare. Add `weights` to `OptimizeJobDto` if the solver should use them.
5. **Passenger names** on plan stops (`passengerName`, optional) are shown when the API sends them; otherwise the booking ref.
6. Role templates: `ETMS_E4_TEMPLATE_PERMISSIONS` (E4-F) give the dispatcher `etms_planning` view/create/edit/command;
   publish also needs `etms_dispatch:command`.
